# Decision D02: Shared Cloudflare D1 & R2 Topology with Environment Isolation

- **Date**: 2026-11-15
- **Spec**: [SPEC-001](../specs/SPEC-001-infra-scaffold.md)
- **Status**: APPROVED

## 1. Context & Problem Statement
We needed to decide whether `backend-client` and `backend-admin` use separate or shared Cloudflare D1 databases and R2 buckets, and which deployment environments are required from Day 1.

## 2. Decision
1. **Shared D1 & R2**: Both Workers bind to the **same shared Cloudflare D1 database** (per environment) and **shared R2 buckets** (`PUBLIC_ASSETS` bucket for published card art/scene media; `PRIVATE_STORAGE` bucket for audio, drafts, and Content Studio artifacts).
   - `backend-admin` holds read/write access to D1 and access to both `PUBLIC_ASSETS` and `PRIVATE_STORAGE` R2 buckets.
   - `backend-client` binds only to D1 (reading published/client-safe tables) and `PUBLIC_ASSETS` R2 (never `PRIVATE_STORAGE`).
2. **Environments**: Configure exactly three isolated environments in Wrangler: `dev` (local `wrangler dev` + `.wrangler/state`), `staging`, and `prod`—each with distinct `database_id`s, R2 bucket names, secrets, and CORS allowlists.

## 3. Rationale
- **Security (#1)**: Least-privilege binding isolation prevents `backend-client` from ever accessing private R2 buckets (`PRIVATE_STORAGE`) and prevents staging/dev workloads from touching production D1/R2 data.
- **Technical Debt (#2)**: Avoids cross-database sync complexity between admin knowledge releases and client reads during Phase 1–2.
- **Speed (#3)**: Single D1 database per environment simplifies local development, migrations, and early domain slices (`SPEC-002`).

## 4. Consequences
- `backend-client` Wrangler config MUST NOT bind `PRIVATE_STORAGE`.
- `staging` and `prod` MUST use separate D1 `database_id`s and R2 buckets; sharing IDs across environments is forbidden.
