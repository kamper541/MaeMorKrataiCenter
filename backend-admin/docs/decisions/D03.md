# Decision D03: Day-1 Admin Auth, Role Hierarchy, JWT/JWKS Rotation & Refresh Sessions

- **Date**: 2026-11-15
- **Spec**: [SPEC-001](../specs/SPEC-001-infra-scaffold.md)
- **Status**: APPROVED

## 1. Context & Problem Statement
Phase 1 has no customer accounts (`backend-client` is public), while `backend-admin` requires immediate Day-1 authentication and role-based authorization so admins/owners (~3 accounts) can mutate D1 data. Deployment starts on **Cloudflare Workers Free tier** (10 ms CPU cap), frontend hosting origin may differ from backend domain (cross-origin), and we plan to migrate to Cloudflare Access Zero Trust later.

## 2. Decision
1. **D1 Auth Schema (`users`, `sessions`, `jwks_keys`, `audit_events`)**:
   - `users`: `id`, `email` (unique lowercase), `password_hash` (versioned string), `role` (`owner` | `admin` | `user`, privilege order `owner > admin > user`), `is_active`, `created_at`, `updated_at`. Self-service signup is disabled (`user` role defined in schema for future phases only).
   - `sessions`: `id`, `user_id`, `token_hash` (SHA-256 only), `family_id`, `expires_at`, `revoked_at`, `replaced_by_session_id`, `created_at`.
   - `jwks_keys`: `kid`, `alg`, `public_jwk_json`, `encrypted_private_key` (AES-256-GCM ciphertext + nonce), `status` (`active` | `retiring` | `revoked`), `created_at`, `expires_at`.
2. **Workers Free-Tier Password Hashing (WebCrypto PBKDF2 + Pepper)**:
   - Use Cloudflare native WebCrypto `SubtleCrypto` **PBKDF2-HMAC-SHA256** at **`100,000` iterations** (the maximum supported by `workerd`) combined with an **HMAC-SHA256 server-side `PASSWORD_PEPPER`** (Wrangler Secret), stored in a versioned format (`$pbkdf2-sha256-peppered$i=100000$...`).
   - **Argon2id** is explicitly deferred to Out of Scope (`TODO-007`) until migrating to Workers Paid tier (or superseded by Cloudflare Access Zero Trust).
3. **Provisioning (`make create-user`)**:
   - No public or secret-gated HTTP bootstrap/signup endpoint. Initial `owner`/`admin` users are created via a local `make create-user` CLI script that hashes passwords (reading password via secure stdin/prompt, never CLI flags) and inserts via `wrangler d1 execute` (`--local`, `--env staging`, `--env prod`).
4. **JWT, Envelope-Encrypted Key Rotation & Cross-Domain Refresh Cookies**:
   - Short-lived asymmetric **`ES256`** access JWTs (15 min TTL) with `kid`, `iss`, `aud`, `sub`, `role`, `jti`, `iat`, `exp`.
   - Private signing keys stored in D1 `jwks_keys` encrypted with **AES-256-GCM** using a 256-bit `KEY_ENCRYPTION_KEY` Wrangler Secret and AAD (`kid || alg`). Public keys served at `GET /.well-known/jwks.json` (`active` + `retiring`).
   - Opaque CSPRNG refresh tokens stored as SHA-256 hashes in `sessions`, single-use rotated with **reuse/replay detection** (revoking the entire `family_id` on replay).
   - Cookie policy: `HttpOnly; Path=/v1/auth` with `SameSite=None; Secure` in `staging`/`prod` (supporting cross-origin frontend hosting) + strict `Origin` allowlist + CSRF custom header check on `/v1/auth/refresh` and `/v1/auth/logout`; `SameSite=Lax` (no `Secure`) in local `dev`.
5. **Zero Trust Readiness**: JWT verifier accepts standard JWKS (`ES256` and `RS256`), enabling future cutover to Cloudflare Access Zero Trust by swapping issuer/JWKS config.

## 3. Rationale
- **Security (#1)**: Envelope encryption (`AES-256-GCM` + `KEY_ENCRYPTION_KEY` Wrangler Secret + `kid` AAD) protects private keys even if D1 leaks alone; `PBKDF2-100k` + secret `PASSWORD_PEPPER` protects password hashes even if D1 leaks alone; zero HTTP bootstrap endpoints eliminates bootstrap attack surface; `SameSite=None; Secure` + strict `Origin` + CSRF header secures cross-origin refresh cookies.
- **Technical Debt (#2)**: Versioned password hash string + JWKS verifier make future Argon2id or Cloudflare Access upgrades non-breaking.
- **Speed (#3)**: Runs natively within Cloudflare Workers Free tier 10 ms CPU budget.

## 4. Consequences
- Raw passwords, raw refresh tokens, `PASSWORD_PEPPER`, and `KEY_ENCRYPTION_KEY` MUST NEVER be stored in D1 plaintext or logged.
- `POST /v1/admin/auth/keys/rotate` MUST be restricted to `owner` role and recorded in `audit_events`.
- Password creation/rotation scripts MUST read secrets/passwords from interactive prompt or stdin, never command-line arguments.
