# Decision D08: English Keys in the Backend, Thai Labels Kept Exactly per Screen

- **Date**: 2026-11-21
- **Spec**: [SPEC-002](../specs/SPEC-002-master-data-to-backend.md)
- **Status**: APPROVED

## 1. Context & Problem Statement
The frontend data uses two label sets for the same relationship statuses:
- `daily-cards.json` has English keys with labels such as `คนรักเก่า`.
- `reading-cards.json` and `reading.ts` use Thai labels as keys (`เลิกกัน`, `คุยกัน`).

Situations for work, money and life exist only as Thai strings.

## 2. Decision
- The backend stores and returns English keys everywhere: categories, situations, love statuses and positions. `reading-cards` maps such as `meanings` and `details` are keyed by English key in API responses.
- Thai labels are stored exactly as each file has them, per screen. For example, `ex_partner` is `คนรักเก่า` on the daily screen and `เลิกกัน` on the 3-card screen, and both are returned.
- Love-status key mapping follows `docs/context/glossary.md`.
- The frontend converts keys to labels itself; the backend owner notifies the frontend owner.

## 3. Rationale
- **Security (#1)**: No impact.
- **Technical Debt (#2)**: One canonical key set for future features (reading engine, analytics) and no Thai strings as identifiers.
- **Speed (#3)**: Small mapping work on the frontend.

## 4. Consequences
- API responses keep today's JSON structure, but the keys of `meanings` and `details` change from Thai labels to English keys.
- Work, money and life situations get new English keys (listed in SPEC-002), confirmed by the developer.
