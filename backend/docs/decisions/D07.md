# Decision D07: Migrations Hold Schema Only; Seed Data Is Loaded Manually

- **Date**: 2026-11-21
- **Spec**: [SPEC-002](../specs/SPEC-002-master-data-to-backend.md)
- **Status**: APPROVED

## 1. Context & Problem Statement
The current frontend JSON (78 cards, daily content, art sizes, taxonomy) must get into D1 once. Options: data inside a migration, an admin import endpoint, or a separate seed the developer runs.

## 2. Decision
- `backend/migrations/` contains schema (DDL) only.
- A copy of the frontend data lives in `backend/seed/`, already stripped of dropped fields (no ChatGPT URLs or other provenance). The backend owns this copy; it never reads `../frontend-client/` at runtime or in scripts (monorepo boundary).
- A seed command turns that data into SQL. The developer runs it by hand from a local terminal against local, staging or prod D1 after deployment.
- The seed is idempotent (upsert by key), so re-running it is safe, and it emits one statement per row to stay under D1 statement-size limits. Suggested questions have no natural key, so the seed gives them stable IDs (`<category>-<n>`). Admin-created suggestions get a server-generated UUIDv4, so they never collide with seed IDs.

## 3. Rationale
- **Security (#1)**: No public or admin import endpoint to attack; provenance links are removed before data enters the backend repo.
- **Technical Debt (#2)**: Schema history stays clean; seed data can be re-run or replaced without new migrations.
- **Speed (#3)**: No import API to build.

## 4. Consequences
- Re-running the seed overwrites admin edits to seeded rows. The developer runs it deliberately, normally once per environment.
- After seeding, the frontend's bundled JSON files can be deleted by the frontend owner.
