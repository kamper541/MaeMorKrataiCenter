# Decision D01: Rust Cloudflare Worker Stack, Axum Router & Shared D1 Migrations Ownership

- **Date**: 2026-11-15
- **Spec**: [SPEC-001](../specs/SPEC-001-infra-scaffold.md)
- **Status**: APPROVED

## 1. Context & Problem Statement
Both `backend-client` and `backend-admin` are being scaffolded in Rust targeting Cloudflare Workers (`wasm32-unknown-unknown`) while maintaining strict monorepo folder isolation (`backend-client/` and `backend-admin/` never import code across folders; contracts live in `../docs/api/`). We needed to select the HTTP routing approach and decide which folder owns canonical D1 SQL migrations for the shared database.

## 2. Decision
1. Use the official `worker` crate (`cloudflare/workers-rs`, `http` + `d1` features) bridged to minimal **`axum`** (`default-features = false`, `json` feature) via `tower-service` and a request-scoped `!Send`/`!Sync` `EnvWrapper`.
2. **`backend-admin/`** owns the canonical shared D1 SQL `migrations/` directory (`../backend-admin/migrations/`). Both `backend-admin` and `backend-client` bind to the shared D1 database IDs per environment.

## 3. Rationale
- **Security (#1)**: Tower/Axum middleware enforces uniform request size limits, security headers, CORS, rate limiting, and structured error handling across every route without ad-hoc handler duplication.
- **Technical Debt (#2)**: Single canonical `migrations/` folder in `backend-admin/` prevents schema drift between services while respecting Rust folder isolation. Stripping Tokio OS/socket features (`mio`) avoids `wasm32-unknown-unknown` build traps.
- **Speed (#3)**: Standard `axum` extractors and `http` crate types speed up future endpoint authoring and testing compared to bespoke `worker::Router` boilerplate.

## 4. Consequences
- Dependencies pulling `tokio` full features, `mio`, or OS-native TLS/sockets are forbidden.
- Crates requiring randomness must enable `getrandom`'s `"js"` / `"wasm_js"` feature.
- Schema migrations MUST be authored and applied from `backend-admin/migrations/` only.
